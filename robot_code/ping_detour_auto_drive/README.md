# auto_drive — 경로 추종 자율주행

`map_nav_test.launch.py` 가 만들어 주는 경로(`/plan`)를 실제로 따라가는 자율주행 기능.
**기존 파일은 하나도 건드리지 않았고**, 이 폴더 안의 파일만 새로 추가했다.

```
~/auto_drive/
  path_follower_node.py     경로 추종 제어기 (/plan + 현재위치 -> /cmd_vel)
  robot_model.urdf          RViz2 RobotModel 용 차체 모델
  auto_drive.rviz           RViz 설정 (로봇모델 + 도면 + 경로 + 추종점/도착 표시)
  auto_drive.launch.py      전부 한 터미널에서 실행 (권장)
  follower_only.launch.py   map_nav_test.launch.py 를 이미 띄운 경우 추종기만 추가
  README.md
```

---

## 웹·Ethernet 브리지 연동

`goal_path_planner_node.py`가 장애물 판정과 A* 재계획을 전담한다.
`path_follower_node.py`는 장애물 토픽을 직접 보지 않고 최신 `/plan`만 추종한다.

| 방향 | 토픽 | 형식/용도 |
|---|---|---|
| 입력 | `/goal_pose` | 새 목적지 |
| 입력 | `/web/replan_request` | 현재 목적지 수동 재계획 |
| 입력 | `/planner/clear_obstacles` | 동적 장애물 임시 기억 초기화 |
| 출력 | `/plan` | 추종기와 웹에 전달할 경로 |
| 출력 | `/planner/status` | 상태·재계획 결과·장애물 좌표 JSON |

동적 장애물은 `obstacle_ttl`(기본 3초) 후 삭제된다. 재계획 직후 같은 길을 즉시
다시 선택하지 않도록 두는 기억도 `blocked_memory_ttl`(기본 3초) 뒤 만료된다.
따라서 장애물을 치우면 자동으로 재시도하고, 계속 영구 장애물로 남지 않는다.

`/planner/status`와 `/plan`은 `control_bridge_node`가 TCP telemetry의 `planner`,
`plan` 필드로 변환하므로 Raspberry Pi 웹은 ROS를 설치하지 않아도 받을 수 있다.

## 1. 실행 방법

### 방법 A — 한 터미널에서 전부 (권장)

```bash
source ~/ros2_ws/install/setup.bash
ros2 launch ~/auto_drive/auto_drive.launch.py
```

띄우는 것: SLAM(slam_bringup) + 도면비교(map_diff_node) + 경로계획(path_planner_node)
\+ **경로추종(path_follower_node)** + UART 모터(UART/node.py) + robot_state_publisher
\+ RViz2(로봇모델 포함).

> 다른 터미널에서 `UART/node.py` 를 이미 돌리고 있다면 `motor:=false` 를 꼭 붙일 것.
> (같은 시리얼 포트를 두 프로세스가 열면 안 된다)

### 방법 B — 기존 런치를 그대로 쓰고 추종기만 얹기

```bash
# 터미널 1 (기존 파일 그대로)
ros2 launch ~/map_path/map_nav_test.launch.py

# 터미널 2
ros2 launch ~/auto_drive/follower_only.launch.py motor:=true
```

이때 로봇모델은 터미널 1 의 RViz 창에서 `Add` → `RobotModel` 을 추가하고
`Description Source = Topic`, `Description Topic = /robot_description` 으로 두면 보인다.
(`follower_only.launch.py` 가 `/robot_description` 을 latched 로 발행한다)

### 다시 실행할 때 run.sh 를 먼저 돌려야 하나? — 아니다

`auto_drive.launch.py` 는 **시작할 때 스스로 청소한다**(`_cleanup_leftovers`).
그냥 다시 `ros2 launch` 하면 된다.

청소는 두 단계다.

1. **이전 `ros2 launch` 부모에게 SIGINT** — 부모가 자기가 띄운 것들(rviz2,
   robot_state_publisher, `UART/node.py`)을 스스로 정리한다. 자식을 이름으로
   지우지 않으므로 **팀원이 띄운 rviz2 를 죽일 위험이 없다**(이 장비는 계정
   하나를 셋이 같이 쓴다).
2. 그래도 남은 고아를 `_OWNED` 패턴으로 마저 제거.

> ★ 신호는 반드시 **SIGINT** 여야 한다. 시험용 런치(자식 `sleep 600` 2개)로 실측:
>
> | 부모에게 보낸 신호 | 부모 | 자식 |
> |---|---|---|
> | `SIGTERM` (`kill`, `pkill -9`) | 죽음 | **그대로 살아남음** |
> | `SIGINT` (Ctrl+C 와 같음) | 죽음 | **같이 정리됨** |
>
> `ros2 launch` 는 SIGINT 에서만 종료 절차를 밟는다. 예전 구현이 SIGTERM 을 써서
> rviz2 와 robot_state_publisher 가 매 실행마다 쌓였고, 그 유령 노드들 때문에
> `ros2 param get` 이 엉뚱한 인스턴스를 읽어 "인자를 줬는데 값이 안 바뀐다"로 보였다.

`run.sh` 는 여전히 쓸모가 있다 — **Ctrl+C 로 끌 때**(`trap cleanup EXIT`) 정리해 주고,
자주 쓰는 인자를 미리 넣어 준다. 실행 전 청소는 런치가 하므로 run.sh 에서 뺐다.

```bash
# 둘 다 됨. 연속으로 몇 번을 실행하든 이전 것은 알아서 정리된다.
ros2 launch ~/auto_drive/auto_drive.launch.py heading_offset:=180.0 robot_radius:=0.12
~/auto_drive/run.sh robot_radius:=0.12
```

### ⚠ 실행 전 반드시 — 다른 /cmd_vel 노드를 모두 끌 것

**`keyboard_test.py` 를 켜 둔 채로 자율주행을 띄우면 로봇이 안 움직인다.**

`keyboard_test.py` 는 키를 안 눌러도 20Hz 로 계속 발행한다 (0.15초 타임아웃 후 강제 0).
그래서 `/cmd_vel` 에 발행자가 둘이 되고, `UART/node.py` 는 콜백에서 **마지막에 온 값으로
덮어쓰기** 때문에 PWM 이 25ms 마다 255 ↔ 0 을 오간다. 모터는 떨기만 하고 로봇은 제자리다.
경로도 정상, TF 도 정상, 명령도 나가는데 안 움직이는 상태라 원인을 찾기 어렵다.

`UART/node.py` 가 두 번 떠 있는 것도 안 된다. 두 프로세스가 같은 시리얼 포트에
동시에 써서 바이트가 섞인다.

```bash
# 남아 있는 수동 조작 노드 정리
pkill -f keyboard_test.py
pkill -f UART/node.py          # launch 가 motor:=true 로 직접 띄우므로

ros2 launch ~/auto_drive/auto_drive.launch.py
```

`node.py` 를 본인 터미널에서 계속 띄워 두고 싶으면 `keyboard_test.py` 만 끄고
`motor:=false` 로 실행하면 된다.

추종기가 3초마다 이 상황을 검사해서 이런 ERROR 를 띄운다:

```
/cmd_vel 에 발행자가 2 개입니다. keyboard_test.py 같은 다른 노드가 0 을 함께 쏘면
명령이 상쇄되어 로봇이 안 움직입니다 — 그 노드를 먼저 끄세요.
/cmd_vel 구독자가 2 개입니다. UART/node.py 가 두 번 떠 있으면 ...
```

### 주행 절차

1. 로봇을 도면상 출발 위치(`start_x`, `start_y`, `start_yaw`, 기본 0.15 / 0.15 / 180°)에 둔다.
2. RViz 상단 **2D Goal Pose** 로 목적지를 찍는다.
3. 초록색 경로가 그려지면 로봇이 **바로 그 경로를 따라 출발**한다.
   (노란 구슬 = 지금 쫓아가는 전방주시점)
4. 목적지 근처에 들어오면 모터가 멈추고 터미널에

   ```
   ==============================================
   목적지에 도착했습니다.
     목적지 (1.20, 0.80) / 현재 (1.18, 0.74) / 오차 0.063 m
   ==============================================
   ```

   가 출력된다.

## 2. 모터 제어 방식

`keyboard_test.py` 와 **완전히 같은 인터페이스**를 쓴다.

| | keyboard_test.py | path_follower_node.py |
|---|---|---|
| 발행 토픽 | `/cmd_vel` (geometry_msgs/Twist) | 같음 |
| 발행 주기 | 20 Hz | 같음 |
| 값 의미 | `linear.x`, `angular.z` | 같음 |
| 종료 시 | 정지 명령 1회 | 정지 명령 전송 |

모든 모터 경로는 발행 직전에 세 가지 primitive로 강제된다.

* 직진/후진: `(linear, angular) = (+/-1, 0)`
* 제자리 회전: `(0, +/-1)`
* 정지: `(0, 0)`

UART에서도 같은 변환을 다시 적용하므로 실제 바퀴 출력은 `-255`, `0`, `255`
외의 값이 나가지 않는다.

### 출력 기본값

| | cmd 범위 | PWM 환산 |
|---|---|---|
| 전진/후진 | +/-1.00 | +/-255 |
| 제자리 회전 | +/-1.00 | 좌우 -255/+255 |
| 정지 | 0.00 | 0 |

이 차체가 낮은 PWM 에서 안 움직여서 최대까지 쓰도록 잡아 둔 값이다.
속도 배율이나 최소/최대 출력 파라미터는 없다. 상위 제어기는
`FORWARD`, `REVERSE`, `TURN_LEFT`, `TURN_RIGHT`, `STOP` 중 하나만 고르고,
UART가 이를 좌우 PWM `-255`, `0`, `255`로 변환한다.

## 3. 제어 방식 (path_follower_node.py)

* **현재 위치**: cartographer 가 발행하는 TF `map -> base_link` 를 20 Hz 로 조회.
  0.6초 이상 오래된 위치면 신뢰하지 않고 정지한다.
* **경로 추종**: pure pursuit.
  현재 위치에서 가장 가까운 경로점을 찾고(진행 방향으로만 전진), 거기서 `lookahead`(0.3 m)
  앞선 점을 목표로 방향 오차를 계산한다.
  * 방향 오차 > 34° → **큰 방향전환** (아래 `turn_mode` 참고)
  * 방향 오차 ≤ 34° → 전진 + 비례 조향, 오차가 클수록 감속
  * 목적지 0.45 m 이내 → 감속

### unknown_is_obstacle — 지도 전체에 목적지를 찍을 수 있게 (기본 false)

`true` 로 두면 아직 라이다가 훑지 않은 곳(RViz 회색)을 전부 벽으로 본다. 그러면
**이미 탐사한 좁은 영역(분홍색) 안에서만** 경로가 나오고, 나머지에 목적지를 찍으면
아무 일도 일어나지 않는다.

기본값을 `false` 로 바꿔 **지도 어디든 목적지를 찍으면 경로가 나온다.** 안 가본 곳의
안전은 추종기의 라이다 비상정지(앞 0.17 m)가 맡는다. 보수적으로 가려면
`unknown_is_obstacle:=true`.

### ★★ 라이다 스캔이 깨지고 있었다 — fixed_resolution (fix_lidar, 기본 true)

**"맵이 이상하다 / 경로가 안 나온다 / 주행이 엉망이고 딜레이가 있다"의 진짜 원인.**

`slam_bringup/config/ydlidar.yaml` 은 `fixed_resolution: true` + `sample_rate: 5` +
`frequency: 10.0` 이다. 이 조합은 회전당 **430점**을 기대하는데, 실제 장치는
**1041점**을 낸다. CPU 부하가 있으면 시리얼 읽기가 밀려 회전 경계를 놓치고,
드라이버가 여러 회전분 점을 430 슬롯에 억지로 담는다.

```
[ydlidar] error: Checksum error 0x1CBC != 0x574B
[ydlidar] warn : Real points 1041 > fixed points 430
[cartographer] W sensor_bridge.cpp:211] Ignored subdivision of a LaserScan message
[cartographer] W range_data_collator.cc:82] Dropped 340 earlier points.
```

각도와 거리가 어긋난 스캔이 되므로 cartographer 가 스캔을 버리고, `/map` 이
**1.08 x 0.82 m** 로 쪼그라들었다(라이다는 7 m 를 보는데도). 그 상태에서는
통행가능 면적이 **0.00 m²** 라 경로가 나올 수가 없다.

같은 CPU 부하에서 실측 비교:

| | `fixed_resolution: true` | **`false`** |
|---|---|---|
| 유효점 | 228/430 (53%) | **295/428 (69%)** |
| 빈 방위구간(10도 × 36) | 8~14개 ★ | **4개 OK** |
| `Real points` 경고 | 27~56회 | **0회** |
| `Ignored subdivision` | 14회 | **0회** |
| `/map` | 1.08 x 0.82 m | **13.2 x 9.8 m** |
| 통행가능 면적 | 0.00 m² | **18.4 m²** |

그래서 `auto_drive.launch.py` 는 라이다를 `slam.launch.py` 에 맡기지 않고
(`use_lidar:=false`) **직접 띄우면서 `fixed_resolution: False` 로 덮어쓴다.**
기존 `ydlidar.yaml` 은 건드리지 않는다. 되돌리려면 `fix_lidar:=false`.

> `range_max` 는 64.0 그대로 둘 것. 12.0 으로 줄여봤더니 먼 벽 읽기가 버려져
> 유효점이 13% 로 떨어졌다.

### map_resolution 기본값 0.05 (0.01 -> 0.05)

`map_resolution:=0.01` 이면 683k 셀 맵을 2초마다 발행해서 CPU 가 포화되고, 그게
위의 라이다 시리얼 밀림을 유발한다. cartographer_node 만 코어 하나의 **86%** 를
쓴다. 경로계획은 0.05 m 격자로 충분하다.

추종기도 CPU 를 12~15% 쓰고 있었다. `/scan` 부채꼴 검사를 파이썬 for 문(430점 x
20Hz)에서 numpy 벡터 연산으로 바꾸고, RViz 마커를 20Hz -> 5Hz 로 줄였다.

### 차체 크기 22 x 18 cm 와 A* 안전반경

실측 차체는 **0.22 x 0.18 m** 다(이전엔 0.19 x 0.123 으로 잘못 잡고 있었다).

로봇은 제자리에서도 돌기 때문에 '폭의 절반'(0.09 m)으로 부풀리면 회전할 때 앞뒤
모서리가 벽에 닿는다. 어느 방향으로 놓여도 안전한 값은 **외접원 반경**이다.

```
반경 = 0.5 * sqrt(0.22² + 0.18²) + 여유 0.02 = 0.1421 + 0.02 = 0.1621 m
```

`live_planner_node.py` 가 이 반경으로 장애물을 부풀린 뒤 그 안에서만 A* 를 돈다.
통로가 좁아 경로가 안 나오면 `robot_radius:=0.11` (폭의 절반+여유) 로 줄이면 된다.

### /planner_inflated 가 맵을 전부 덮지 않던 문제

계획 격자를 만들 때 `h // f` 로 잘라내서 끝단 최대 f-1 셀이 빠졌고, 그 바깥을
목적지로 찍으면 "맵 밖"이라며 경로가 안 나왔다. 잘라내지 말고 **장애물로 패딩**해서
`/map` 전체 범위를 덮도록 고쳤다. 실측 커버리지 0.95 -> **1.00**.

### start_x / start_y / start_yaw 는 IMU 기준인가 라이다 기준인가

`my_robot.lua` 와 static TF 를 보면 답이 나온다.

```
tracking_frame  = "imu_link"     -- cartographer 가 추적하는 프레임
published_frame = "base_link"    -- TF 로 내보내는 프레임
use_imu_data    = true

base_link -> laser_frame :  x 0, y 0, z 0.1,  yaw 0, roll 180도
base_link -> imu_link    :  x 0, y 0, z 0.05, yaw 0, roll 0
```

* **위치 (start_x, start_y)** — 라이다와 IMU 가 **둘 다 x=0, y=0** (z 만 다르다).
  즉 어느 쪽 기준이든 같은 점이고, 그 점은 `base_link` = 로봇의 회전 중심이다.
  위치는 센서를 구분할 필요가 없다.
* **방향 (start_yaw)** — 두 static TF 모두 `yaw 0` 으로 **선언**돼 있다. 즉
  "라이다의 0도 = IMU 의 앞 = base_link 의 +x" 라고 선언만 해 둔 상태다.
  map 프레임의 절대 방향은 **첫 스캔**으로 고정되므로, 실질적으로
  **`start_yaw` 는 라이다의 0도 표시가 향한 방향**이다.
  IMU 는 중력 정렬과 각속도 적분만 담당한다.
  (`align_check.py` 가 스캔을 도면에 맞춰 값을 내는 것도 같은 기준이라 일관된다)

**따라서 라이다가 차체에 대해 돌려 장착돼 있으면 `base_link` 의 +x 는 로봇의 앞이
아니다.** 그 선언(`yaw 0`)이 틀린 것이고, 아래 `heading_offset` 이 그 차이를 메운다.
`start_yaw` 는 그대로 라이다 기준으로 두면 된다 — 둘은 서로 다른 것을 보정한다.

| | 무엇을 맞추나 | 기준 |
|---|---|---|
| `start_x/y/yaw` | map 원점이 **도면 위 어디에** 있나 | 라이다(=첫 스캔) |
| `heading_offset` | base_link 의 +x 가 **차체의 앞과 얼마나 어긋났나** | 실제 이동 방향 |

### ★ base_link 의 +x 가 정말 로봇의 앞인가? (heading_offset)

**"출발할 때 180도 돌고 나서 초록 경로를 안 따라가고 맵을 벗어난다"는 증상의 정체.**

`slam.launch.py` 의 static TF 는 이렇게 선언한다.

```
base_link -> laser_frame :  --x 0 --y 0 --z 0.1 --yaw 0 --pitch 0 --roll 3.14159
```

`--yaw 0` 이므로 cartographer 는 **base_link 의 +x = 라이다의 +x** 라고 믿는다.
그런데 라이다가 차체에 대해 yaw 로 돌아 장착돼 있으면(커넥터/케이블이 뒤를 향하게
180도 돌려 붙이는 경우가 흔하다) **base_link 의 +x 는 로봇의 앞이 아니다.**

이때 나타나는 증상이 정확히 이렇다.

* 위치 추적은 **완벽해 보인다** — 지도와 궤적이 서로 일관되므로 이상해 보이지 않는다
* 수동 키보드 조작도 **완벽하다** — 사람이 눈으로 보고 조작하니 좌표계와 무관하다
* 그런데 추종기는 base_link +x 를 '앞'으로 믿고 방향오차를 계산한다. "전진" 명령을
  내리면 로봇은 추종기가 믿는 방향과 다른 쪽으로 간다 → 오차가 커진다 → 크게 돌고
  → 계속 어긋나며 맵을 벗어난다

시뮬레이터로 재현·검증한 결과 (경로는 로봇 정면 1.2m 직진 후 좌회전):

| 조건 | 결과 | 경로 최대이탈 |
|---|---|---|
| 정상 장착 | 도착 | 0.080 m |
| **라이다 180도 어긋남, 보정 없음** | **미도착 (-22.40, -3.21)** | **22.6 m** |
| 라이다 180도 어긋남, `heading_offset:=180` | 도착 | 0.078 m |

가운데 줄이 바로 이 증상이다.

#### 자동 보정 (auto_heading_offset, 기본 true) — 이제 측정 안 해도 된다

새 경로를 받으면 추종기가 먼저 0.10 m 직진한다(`first_move_forward`). **그 직진이
곧 '앞이 어디인가' 측정이다.** 실제 이동 방향과 TF yaw 가 20도 이상 다르면 그 자리에서
`heading_offset` 을 보정하고 계속 주행한다.

```
[INFO ] 새 경로 수신: 84점, 길이 3.30 m ...
[INFO ]   로봇 방향 +2도 | 경로 시작방향 -178도 | 방향오차 -180도
          -> 크게 돌아야 함 (경로가 로봇 뒤에서 시작)
[ERROR] ★ 자동 보정: 전진했더니 실제로는 -180도 방향으로 갔습니다.
        base_link 의 +x 가 로봇의 앞이 아닙니다. heading_offset 을 -180도 로 잡고 계속합니다.
```

시뮬레이터 검증 (경로는 로봇 정면 1.2m 직진 후 좌회전):

| | 방향오차 진단 | 자동보정 | 결과 | 경로 최대이탈 |
|---|---|---|---|---|
| 정상 장착 | +0도 (바로 전진) | 불필요 | 도착 | 0.082 m |
| 라이다 180도 어긋남 | -180도 (뒤에서 시작) | **-180도 적용** | 도착 | **0.067 m** |

보정 전 같은 조건에서는 22.6 m 를 벗어났다. 매번 재는 게 싫으면 로그에 찍힌 값을
`heading_offset:=-180.0` 으로 고정하면 된다. 끄려면 `auto_heading_offset:=false`.

#### 왜 도는지 한 줄로 보기

경로를 받을 때마다 이 줄이 찍힌다. 원인 구분이 바로 된다.

* `방향오차 +5도 -> 바로 전진` : 정상
* `방향오차 -180도 -> 크게 돌아야 함` : 경로가 로봇 뒤에서 시작.
  RViz 에서 로봇 **앞쪽(주황색 면)** 이 초록 경로를 향하고 있는데도 이 값이 나오면
  base_link 방향이 실제와 다른 것이고, 위 자동 보정이 잡아준다.

#### 수동 측정: heading_check.py

```bash
# 자율주행 launch 를 motor:=true 로 띄운 상태에서 (앞이 트인 곳에서)
python3 ~/auto_drive/heading_check.py
python3 ~/auto_drive/heading_check.py --dry-run   # 안 움직이고 사전점검만
```

전진 명령을 0.6초 주고, TF 로 관측한 **실제 이동 방향**과 그때의 yaw 를 비교한다.

```
heading_offset = atan2(dy, dx) - yaw
```

0도 근처면 정상, 180도면 라이다가 뒤를 보고 장착된 것. 앞쪽 여유를 라이다로 먼저
확인하고 부족하면 실행을 거부한다. 좌회전 부호(`invert_angular`)도 같이 측정한다.

#### 적용

```bash
ros2 launch ~/auto_drive/auto_drive.launch.py heading_offset:=180.0
```

추종기는 `TF yaw + heading_offset` 을 로봇의 실제 앞 방향으로 쓴다.
근본적으로 고치려면 `slam.launch.py` 의 static TF 를 `--yaw 3.14159` 로 바꾸면 되지만,
그 파일은 기존 패키지라 건드리지 않고 이 파라미터로 처리한다.

#### 자동 진단

측정을 안 해도 추종기가 스스로 잡아낸다. 전진 명령을 냈을 때의 실제 이동 방향을
누적해서 비교하고, 30도 이상 어긋나면 ERROR 를 띄운다.

```
[ERROR] 전진 명령에 로봇이 +180 도 어긋난 방향으로 갑니다 (6회 관측).
        base_link 의 +x 가 로봇의 앞이 아닙니다 — 라이다가 차체에 대해 돌아
        장착된 경우입니다. heading_offset:=180.0 을 주고 다시 실행하세요.
```

### ★ 제자리 회전이 안 되는 건 출력 부족이 아니다 — 회전 펄스 (turn_pulse_off)

차체 위에 무게가 얹히면 제자리 회전을 못 하던 문제. 원인을 두 가지로 나눠 봤다.

**1) 모터 출력 부족? — 아니다.** 모든 0이 아닌 명령은 공통 primitive 변환과
UART의 이중 방어를 거쳐 절댓값 255로 출력된다:

```
직진: left=+255, right=+255
회전: left=-255, right=+255 (반대 방향은 부호 반대)
```

회전 명령은 `TURN_LEFT` 또는 `TURN_RIGHT`이고 UART 변환 결과는 처음부터
절댓값 255다. 여기서 더 올릴 여지가 없다.

**2) 명령 구조? — 이쪽이다.** 회전은 `turn_pulse_on`/`turn_pulse_off` 로 끊어서
줬는데 기본이 4/2 였다. 20 Hz 기준으로:

```
예전 (on=4, off=2)   aaaa..aaaa..aaaa..aa    회전 듀티  70%
지금 (on=4, off=0)   aaaaaaaaaaaaaaaaaaaa    회전 듀티 100%
```

**300 ms 마다 100 ms 씩 완전히 멈춘다.** 상판이 무거우면 그때마다 관성으로 멈춰
버리고, 다시 돌 때 정지마찰을 처음부터 다시 깨야 한다. 그래서 못 도는 것이다.
원래 이 펄스는 비례제어가 없는 keys 모드에서 오버슛을 줄이려고 넣은 것이었다.

그래서 **`turn_pulse_off` 기본값을 0 으로** 바꿔 연속 회전시킨다. 오버슛은
히스테리시스(`key_turn_on` 0.35 rad 에서 켜고 `key_turn_off` 0.15 rad 에서 끔)와
20 Hz 제어주기가 잡는다. 만약 목표 각도를 지나쳐 좌우로 헌팅하면 `turn_pulse_off:=1`
정도로 올리면 된다.

```bash
# 회전이 여전히 무겁다  -> 이미 PWM 최대치이므로 기구/전원 쪽 문제다
# 좌우로 헌팅한다        -> turn_pulse_off:=1 또는 2
ros2 launch ~/auto_drive/auto_drive.launch.py heading_offset:=180.0 turn_pulse_off:=1
```

### 회전이 목표를 지나치는 문제 — 예측 정지 (turn_lead_sec)

연속 회전으로 바꾸고 나니 잘 돌긴 하는데 **원하는 각도보다 조금 더 돌았다.**
명령을 끊어도 로봇이 즉시 서지 않기 때문이다. 지연은 두 군데서 온다.

```
TF(자세) 갱신 지연   0.1~0.2 초   +   모터 관성(감속 시상수)  0.15~0.35 초
```

회전 각속도가 90도/s 라면 이 둘을 합쳐 **30도 넘게 더 돈다.** 임계값을 키워서
일찍 끄는 방법도 있지만, 그러면 작은 각도는 아예 회전을 시작하지 않게 된다.

그래서 **매 주기 "지금 속도로 계속 돌면 지나치는가"를 판단**한다.

```python
coast = abs(self.yaw_rate) * self.turn_lead   # 앞으로 더 돌 각도
if coast > abs(err) - self.key_turn_off:
    return 0.0, 0.0                            # 이번 주기는 쉬어서 미리 감속
```

`yaw_rate` 는 TF 로 잰 **실제** 각속도다(지수평활). 그래서 빨리 돌 때는 일찍 끊고,
느리면 늦게까지 붙는다. 큰 각도를 돌 때는 남은 각이 훨씬 크므로 그대로 연속
최대출력이라 정지마찰 문제도 안 생긴다. 목표 근처에서만 저절로 톡톡 끊기며 접근한다.

여러 조건(회전속도 60~140도/s, 시상수 0.15~0.35 s, 지연 0.10~0.20 s)에서
목표각 25~180도를 시뮬레이션한 평균 최종 오차:

| `key_turn_off` \ `turn_lead_sec` | 0.0 | 0.2 | 0.3 | **0.4** | 0.5 |
|---|---|---|---|---|---|
| **8.6도 (기본)** | 15.7도 | 9.5도 | 7.2도 | **6.2도** | 6.2도 |
| 6.0도 | 17.1도 | 10.4도 | 8.1도 | 7.0도 | 6.8도 |
| 4.0도 | 18.0도 | 11.5도 | 8.8도 | 7.9도 | 7.6도 |

`turn_lead_sec` **0.4** 에서 최소(15.7도 → 6.2도, 2.5배 개선). 정지 데드밴드
(`key_turn_off`)는 오히려 **줄이면 나빠진다** — 더 바짝 쫓다가 더 크게 지나치기
때문이다. 그래서 0.15 rad 그대로 둔다.

```bash
# 아직도 지나친다  -> 키운다
ros2 launch ~/auto_drive/auto_drive.launch.py heading_offset:=180.0 turn_lead_sec:=0.5
# 목표에 못 미친다 -> 줄인다
ros2 launch ~/auto_drive/auto_drive.launch.py heading_offset:=180.0 turn_lead_sec:=0.3
```

### first_move_forward — 첫 동작은 무조건 전진 (기본 false 로 변경)

원래는 기동 직후 180도 헛도는 걸 막으려고 켜 뒀는데, **경로 방향과 상관없이 무조건
앞으로 나가므로 출발부터 경로를 벗어난다.** `heading_offset` 을 제대로 주면 필요
없으므로 **기본값을 false 로 바꿨다.** 이제 처음부터 경로를 따라간다.

> 이 강제 전진 구간이 `auto_heading_offset` 의 측정 구간이기도 했다. 꺼 두면
> 출발 시 자동 보정은 하지 않으므로 `heading_offset` 을 직접 줘야 한다.
> 주행 중 보정(`check_forward_direction`)은 그대로 동작한다.

### (참고) 예전 설명 — first_move_forward 를 켰을 때의 동작

새 경로를 받으면 방향오차가 크더라도 **제자리 회전부터 하지 않고** 먼저
`first_forward_dist`(기본 0.10 m) 만큼 전진한 뒤 정상 추종으로 넘어간다.
라이다 비상정지는 이 구간에도 살아 있으므로 벽으로 밀고 들어가지는 않는다.
끄려면 `first_move_forward:=false`.

### 경로계획은 기준 도면 기준 (planner:=reference, 기본값)

> **정정.** 한때 "도면은 1x1 m 인데 실제 공간은 7.3x5.1 m 라 도면을 못 쓴다"고 판단해
> `live` 를 기본으로 바꿨었다. **그 측정이 틀렸다.** 당시 라이다 스캔이 깨져 있어서
> (위 `fixed_resolution` 항목) 각도가 뒤섞인 점들이 실제보다 훨씬 넓게 퍼져 보였던 것이다.
>
> 라이다를 고친 뒤 다시 재니:
>
> | | 깨진 스캔 | **실제** |
> |---|---|---|
> | 최대 거리 | 6.77 m | **0.82 m** |
> | 점구름 크기 | 7.30 x 5.10 m | **0.68 x 0.99 m** |
>
> **방은 1 m x 1 m 가 맞다.** 도면 `room_shelf5.yaml` 과 일치하므로
> `path_planner_node.py`(도면 기반) 가 맞는 선택이다. 기본값을 되돌렸다.
> `live` 는 도면이 없거나 넓은 공간에서 쓰면 된다.

### 코너에서 벽에 닿을 때 — 부풀림 + lookahead 를 같이 봐야 한다

부풀림만 키워서는 안 된다. **경로가 벽에서 얼마나 떨어져 있나** 와
**추종기가 경로를 얼마나 정확히 타나** 를 같이 봐야 한다.

```
허용 이탈 = (경로가 벽에서 떨어진 거리) - (차체 반폭 0.09)
```

| 설정 | 경로~벽 | 허용 이탈 | 90도 코너 실측 이탈 | 결과 |
|---|---|---|---|---|
| 예전 (반경 0.11, lookahead 0.30) | 0.11 m | 0.02 m | **0.075 m** | 여유의 3.8배 → 닿음 |
| 반경만 키움 (0.13, lookahead 0.30) | 0.13 m | 0.04 m | 0.075 m | 여유의 1.9배 → 여전히 닿음 |
| **현재 (반경 0.13, lookahead 0.12)** | **0.13 m** | **0.04 m** | **0.029 m** | **여유 안 → 안 닿음** |

* `robot_radius:=0.11` (+margin 0.02 = **0.13**) — 이 방에서 쓸 수 있는 **최대값**.
  0.135 이상이면 로봇 출발 자리(벽까지 0.130 m)가 금지영역이 되어 출발조차 못 한다.
* `lookahead:=0.12` — 전방주시 거리가 크면 코너를 크게 자른다.
  실측 0.30 -> 0.075 m, 0.18 -> 0.043 m, 0.12 -> 0.029 m.

**대가**: 부풀림을 키우면 갈 수 있는 영역이 0.197 -> **0.101 m²** 로 줄어든다.
멀거나 구석진 목적지는 "경로 없음" 이 날 수 있다. 그럴 땐 되돌리면 된다.

```bash
# 벽에 닿아도 되니 더 멀리 가고 싶을 때
ros2 launch ~/auto_drive/auto_drive.launch.py robot_radius:=0.09
# 중간값
ros2 launch ~/auto_drive/auto_drive.launch.py robot_radius:=0.10
```

### 안전반경은 '폭의 절반', 외접원이 아니다 (robot_radius, 기본 0.09)

이 방은 **가장 넓은 통로가 0.36 m** 다(벽에서 가장 먼 지점 0.180 m).
차체 0.22 x 0.18 m 를 제자리 회전까지 안전하게 감싸려면 외접원 반경 0.1421 m 가
필요한데, 그 값으로 부풀리면 갈 수 있는 곳이 거의 사라진다.

| 반경 | 설명 | 주행가능 면적 |
|---|---|---|
| 0.1621 m | 외접원 + 여유 | **0.009 m²** (경로 안 나옴) |
| 0.1421 m | 외접원 | 0.045 m² |
| **0.110 m** | **폭절반 + 여유 (기본)** | **0.197 m²** |
| 0.090 m | 폭절반 | 0.253 m² |

`robot_radius` 에 `safety_margin` 이 더해진다(0.09 + 0.02 = 0.11).
원래 `path_planner_node.py` 가 `0.5*폭` 을 기본으로 쓴 이유가 이것이고,
그 주석에도 "외접원 반경을 쓰면 좁은 통로에서 경로가 아예 안 나올 수 있다"고 적혀 있다.

> **물리적 한계 하나.** 통로 폭 0.36 m 인데 차체가 회전하려면 0.284 m 지름이 필요하다.
> 즉 **이 미로 안에서는 대부분의 지점에서 제자리 회전을 할 수 없다.** 통로를 따라
> 정렬해서 지나가는 것만 가능하다. 큰 방향전환이 필요한 경로는 애초에 무리다.

### (참고) 실시간 SLAM 맵 기반 플래너 — planner:=live

**기준 도면(`room_shelf5.yaml`)은 1.0 x 1.0 m 인데 로봇이 있는 실제 공간은
7.3 x 5.1 m 였다.** 라이다 스캔점의 **18%** 만 도면 안에 들어와서, `start_x/start_y/
start_yaw` 를 어떻게 맞춰도 정렬이 불가능했다. 로봇이 "맵을 벗어나는" 근본 원인이
이것이다 — 정렬 파라미터로 고칠 문제가 아니었다.

`live_planner_node.py` 는 cartographer 의 실시간 `/map` 위에서 직접 A* 를 돈다.

| | 기존 `path_planner_node.py` | 새 `live_planner_node.py` |
|---|---|---|
| 지도 | 정적 도면 yaml | 실시간 `/map` |
| 정렬 | `start_x/y/yaw` 필요 | **불필요** (`/map` 이 이미 로봇 좌표계) |
| 출발점 | 항상 SLAM 시작 자리 | **지금 로봇이 있는 자리** (TF) |
| 미탐사 영역 | 개념 없음 | 기본 벽으로 취급 (`unknown_is_obstacle`) |

검증: 3.30 m 경로 84점 생성, **경로 시작점이 로봇 실제 위치에서 0.005 m**.

되돌리려면 `planner:=reference`.

#### 알아둘 것 — 통행가능 영역이 쪼개진다

지도를 만들다 보면 통행가능 영역이 여러 덩어리로 끊긴다 (아직 안 이어진 곳, 좁아서
차체 여유를 넣으면 끊기는 곳). 실측에서 11개 덩어리가 나왔고 로봇은 가장 큰 덩어리
(7.09 m²)에 있었다. **다른 덩어리(50셀짜리 섬 등)를 목적지로 찍으면 A* 는 당연히
실패한다.**

그래서 목적지가 로봇과 이어져 있지 않으면 **갈 수 있는 가장 가까운 곳으로 옮겨** 준다.

```
[WARN] 목적지가 로봇과 이어져 있지 않습니다 — 갈 수 있는 가장 가까운 곳으로
       0.12 m 옮겼습니다. (지도가 더 만들어지면 원래 지점까지 갈 수 있습니다)
```

끄려면 `snap_to_reachable:=false`. 처음엔 지도가 거의 없으니 로봇을 조금 몰아서
주변을 훑어 준 뒤 목적지를 찍는 게 좋다. 급하면 `unknown_is_obstacle:=false` 로
미탐사 영역도 통행 가능으로 볼 수 있다(라이다 비상정지에 의존하게 되므로 덜 안전).

> 경로점 간격도 중요하다. A* 결과를 직선 구간에서 줄이면 3m 경로가 4점이 되는데,
> 추종기는 경로점을 따라 걸어가며 lookahead 를 찾으므로 그러면 전방주시 0.3m 가
> 사실상 무의미해진다. `path_spacing`(기본 0.04m)으로 균일하게 다시 찍는다.

### (참고) 도면 정렬 — align_check.py

map 프레임의 원점은 **로봇이 SLAM 을 시작한 자리**이고, 그 자리가 도면 위 어디에
어느 방향으로 있는지는 `start_x / start_y / start_yaw` 로 사람이 알려준다.
이 값이 틀리면 경로계획이 벽 위치를 잘못 알아서 이상한 경로가 나온다.
**추측하지 말고 라이다로 재라.**

```bash
# 자율주행 launch 를 띄운 상태에서 (로봇은 움직이지 않는다, 읽기만 함)
python3 ~/auto_drive/align_check.py
```

스캔점을 도면으로 옮겨 **벽 표면까지의 평균거리**가 최소가 되는 정렬을 격자탐색한다.
각도별 점수 분포도 같이 찍어 주므로 180도 뒤집힘인지 눈으로 바로 확인된다.

> 점수는 반드시 **벽 표면**까지의 거리로 재야 한다. 벽 내부까지의 거리
> (`distanceTransform(free)`)를 쓰면, 이 도면처럼 벽이 두꺼우면(전체의 24%)
> 아무 정렬에서나 점이 벽 속에 떨어져 거리 0 이 되어 지표가 포화된다.
> 처음에 그렇게 만들었다가 모든 후보가 0.000 으로 나와서 고쳤다.

실제 측정 예 (room_shelf5, 1m x 1m 방):

```
현재 설정  start_x=0.15 start_y=0.15 start_yaw=180.0
           오차 0.040 m, 도면 안에 들어온 점 85%
측정 결과  start_x=0.07 start_y=0.21 start_yaw=159.0
           오차 0.010 m, 도면 안에 들어온 점 100%
```

각도별 분포에서 최소점이 150~165도에 뚜렷하고, 반대편(336도)은 2.7배 나빴다
→ **180도 뒤집힘이 아니라 21도 + 8cm 어긋남**이었다.

이 도면은 형태가 180도 회전대칭에 가깝다(선반 두 개가 서로 반대편에서 뻗어나옴).
그래서 눈으로 보면 뒤집힌 것처럼 느껴지기 쉽다. 점수가 앞뒤로 비슷하게 나오면
스캔만으로는 못 가리므로, `w` 를 1초 눌러 실제 이동 방향과 RViz 를 비교하면 된다.

### 자동 정렬 탐색 — 조대 → 정밀 2단계 (auto_align_node.py)

`auto_align_node` 는 위 측정을 매 실행 자동으로 해서 `start_x/y/yaw` 를 다른 노드에
바로 넣어 준다. 처음에는 **한 겹짜리 격자탐색**이었는데, 전 범위(±0.30 m, 0~360도)를
훑어야 하니 해상도를 올릴 수가 없었다. `xy_step 0.02` / `yaw_step 2.0` 이 한계였고
후보가 이미 31×31×180 = **172,980** 개였다.

문제는 이게 느린 것보다 **부정확**하다는 것이었다. 답이 격자 위에 없으면
격자 간격의 절반(±1 cm / ±1도)이 그대로 오차로 남는다. 실제 로그에서
`start_yaw 356.0 -> 358.0` 으로 2도씩 튀면서 오차가 `0.0305 m` 에서 안 줄던 이유다.

그래서 두 단계로 나눴다. 성기게 훑어 대략 위치를 잡고(`coarse_xy_step 0.05` /
`coarse_yaw_step 5.0`), 그 주변만 촘촘히 다시 본다(`xy_step 0.01` / `yaw_step 0.5`).
정밀 단계가 보는 범위(`fine_span_xy 0.06` / `fine_span_yaw 6.0`)는 조대 격자 간격보다
넓게 잡아서 두 단계 사이에 빈틈이 생기지 않게 했다.

도면에 알려진 자세로 스캔을 만들어 넣고 잰 결과 (스캔 15% 소실 + 10% 가짜반사, 6회 평균):

| | 옛 설정 (단일 격자) | 새 설정 (조대→정밀) |
|---|---|---|
| 평균 위치오차 | 10.0 mm | **4.8 mm** |
| 평균 각도오차 | 0.17도 | 0.16도 |
| 탐색 시간 | 3.33초 | **0.58초** |
| `score()` 호출 | 25,920회 | 4,911회 |
| 최종 해상도 | ±1 cm / ±1도 | **±0.5 cm / ±0.25도** |

정답을 ±10 cm / ±8도 로 넓게 흩뿌린 20회 스트레스 시험에서도, 크게 빗나간 경우는
옛 설정 6회 / 새 설정 4회였고 **새 설정만 실패한 경우는 0회**였다(실패 4건은 옛 설정도
같이 실패). 20회 중 19회에서 새 탐색이 더 낮은 score, 즉 더 좋은 최적해를 찾았다.

여기에 `settle_sec` 을 8.0 → **3.0** 초로 줄였다. 이건 SLAM 이 안정될 때까지 기다리는
시간인데, 라이다가 붙고 첫 스캔이 들어오는 데 실제로 그렇게 오래 걸리지 않는다.
정렬이 끝나기까지 **11.3초 → 3.6초**.

로그 끝에 `| 탐색 N.N초` 가 붙으므로 실제 걸린 시간을 바로 확인할 수 있다.
정렬이 불안하면 `coarse_yaw_step:=2.5` 처럼 조대 단계만 촘촘히 하면 된다.

### ★★ 자동정렬이 아무것도 안 하고 있었다 — coverage 게이트 (max_point_range)

"라이다 스캔과 도면이 어긋나 있는데 자동정렬이 안 된다"는 증상의 진짜 원인.
실행 132초 뒤에 `start_x/y/yaw` 를 읽어 보니 **기본값 그대로**였다. 즉 자동정렬이
값을 넣은 게 아니라 **한 번도 못 넣은** 것이다.

탐색은 점구름이 도면 안에 `min_coverage`(0.85) 이상 들어온 후보만 인정하는데,
**어떤 후보도 그 선을 못 넘고 있었다.** 실측:

```
조대 탐색 | 자세가능 후보 1296개 | 그중 cov>=0.85 통과 0개 | 최대 cov 82%
```

이유는 방이 도면보다 넓기 때문이다. 도면은 1.95 x 1.62 m 인데 스캔은 **5.4 m** 까지
나간다. 미로가 트인 오른쪽으로 라이다가 바깥 방까지 보고, 그 점들이 전부 '도면 밖'으로
세어져 coverage 를 깎아먹는다. 후보가 없으니 `best = None` → "정렬을 못 찾았습니다"
경고 한 줄 남기고 `applied = True` 로 재시도를 멈춘다 → 도면은 어긋난 채로 방치.

**도면 대각선보다 먼 점은 로봇이 도면 안에 있는 한 기하학적으로 절대 도면 안에
들어올 수 없다.** 그래서 그런 점은 아예 버린다(`max_point_range`, 기본 0 = 도면 대각선).

| | 자르기 전 | 대각선(2.54 m)로 자름 |
|---|---|---|
| 쓰는 점 | 1587개 | 1336개 (251개 버림) |
| 최대 coverage | 82% | **98%** |
| 게이트 통과 후보 | **0개** | 355개 |
| 정렬 오차 | 0.0343 m | **0.0220 m** |

여기에 두 가지를 더 했다.

- `min_coverage` 를 파라미터로 뺐다.
- 그래도 통과 후보가 0개면 **포기하지 않고**, 실제로 닿은 최대 coverage 의 95% 로
  기준을 한 번 낮춰 다시 맞춘다. 조용히 아무것도 안 하는 것이 제일 나쁘다.
- 끝내 실패하면 경고가 아니라 **에러**로, "start_x/y/yaw 가 기본값 그대로 남아
  도면이 어긋나 보일 것"이라고 명시한다.

### ★★★ 정렬이 실행마다 흔들리던 진짜 원인 — 각도를 먼저 못 박아라 (벽 방향)

"잘 되다가도 안 된다"의 원인. 이 미로는 같은 빗살이 규칙적으로 반복돼서,
0~360도를 다 훑으면 **점수가 거의 같은 별칭(alias) 해가 잔뜩 나온다.** 그래서
잴 때마다 다른 것에 걸린다. 정지한 로봇을 연속으로 잰 실측:

```
yaw 341.0  오차 0.0388      y 1.45
yaw   0.0  오차 0.0346      y 1.10
yaw   5.5  오차 0.0400      y 1.28
yaw   1.5  오차 0.0353      y 1.36     <- y 가 35cm 벌어졌는데 오차는 동률
```

해법은 **위치보다 각도를 먼저 확정**하는 것이다. 각도는 별칭에 안 흔들리는
독립적인 단서가 있다 — **벽 방향**이다. 도면의 벽은 전부 직각이므로, 스캔점들의
국소 방향을 0~90도로 접어 히스토그램을 만들면 한 곳에 뾰족하게 몰린다.

도면은 map 프레임에 `R(-yaw)` 로 그려지므로 도면의 직각 벽은 map 에서
`(-yaw) mod 90` 방향으로 보인다. 즉 지배적 벽 방향이 `w` 면

```
start_yaw = -w  (mod 90)   ->  후보는 90도 간격으로 딱 4개
```

이 4개 주변(`wall_span`, 기본 ±5도)만 보면 된다. 각도 후보가 72개(5도 간격
전 범위)에서 12개로 줄어 **빨라지고**, 별칭이 애초에 후보에서 빠지니
**흔들리지 않는다**.

계산은 KD-tree 없이 O(n) 이다. 스캔은 각도 순서로 들어오므로 이웃한 점이 곧
같은 벽면 위의 점이다. 연속 3점의 방향만 보면 되고, 벽을 건너뛴 구간은 두 점
간격(`wall_seg_max`, 기본 0.06 m)으로 걸러낸다.

실측 (정지한 로봇, 같은 자리에서 3번 연속):

| | 이전 (전 범위 탐색) | **지금 (벽 방향 제한)** |
|---|---|---|
| x 재현성 | 1.64 ~ 1.88 (240 mm) | **1.57 / 1.57 / 1.57 (0 mm)** |
| y 재현성 | 1.10 ~ 1.45 (350 mm) | **1.38 / 1.38 / 1.38 (0 mm)** |
| yaw 재현성 | 341 ~ 5.5도 (32도) | **353.2 ~ 354.8도 (1.6도)** |
| 오차 | 0.035 ~ 0.040 | **0.018 ~ 0.020** |
| 탐색 시간 | 3.33초 | **0.4초** |

로그에 `벽 방향 3도 (점의 72%가 이 방향) -> yaw 후보 87, 177, 267, 357` 처럼 찍힌다.
봉우리 집중도가 `wall_share_min`(기본 45%)에 못 미치면 — 방이 직각 구조가 아니거나
스캔이 나쁘면 — 경고를 내고 예전처럼 전 범위를 훑는다.

### ★★★ "잘 되다가도 안 되는" 진짜 이유 — SLAM 이 가만히 있어도 움직인다

정렬을 아무리 정확히 맞춰도 시간이 지나면 어긋나는 이유. **로봇이 완전히 정지해
있어도 cartographer 의 pose 는 계속 변한다.** `map -> base_link` 를 98초간 5초마다
찍어 본 실측:

```
 47s   y +216.4 mm   yaw -7.17도
 52s   y +199.5 mm   yaw -5.48도   <- 한 번에 y 17 mm + yaw 1.7도 점프 (최적화)
 98s   y +200.0 mm   yaw -5.76도
총 변동:  x 16 mm | y 27 mm | yaw 2.29도
```

스캔 전체가 map 안에서 그만큼 통째로 움직이므로, **처음에 한 번 맞춘 도면은 반드시
어긋난다.** 예전 기본값은 `refine_sec=0`(한 번 재고 끝)이라 그대로 방치됐다.

그래서 **계속 다시 재서 따라간다**(`refine_sec`, 기본 3초). 다만 매번 전역 탐색을
하면 느리고(2.4초) 빗살 옆 별칭으로 튈 위험까지 생기므로, 두 단계로 나눴다.

| | 획득(처음 1회) | 추적(그 뒤 계속) |
|---|---|---|
| 탐색 범위 | `xy_range` 0.30 m, yaw 후보 4개 | `track_xy_range` 0.06 m, `track_yaw_range` ±2.5도 |
| 후보 정밀화 | 상위 `coarse_topk` 6개 전부 | 직전 값 주변 1개 |
| 측정 합의 | 3회 일치해야 적용 | 생략 (자리를 이미 알고 있으므로) |
| 걸리는 시간 | 2.4초 | **0.8~1.5초** |

적용 조건은 "지금 값보다 점수가 낮을 때만"이라, 잡음으로 나빠지는 쪽으로는 안 끌려간다.

실제 동작 로그 — 드리프트로 오차가 벌어질 때마다 다시 당겨온다:

```
정렬 측정: start_x 1.72 -> 1.78 | start_y 1.39 -> 1.11 | start_yaw 356.0 -> 352.6
           (오차 0.0289 -> 0.0130 m, 도면내 점 42% -> 86%) | 탐색 2.4초
정렬 추적: x=1.720 y=1.192 yaw=353.7 (오차 0.0094 -> 0.0090 m) | 1.55초
정렬 추적: x=1.717 y=1.190 yaw=353.6 (오차 0.0103 -> 0.0097 m) | 1.52초
```

### ★ 조대 단계에서 1등만 들고 가면 안 된다 (coarse_topk)

빗살 한 칸(0.31 m) 옆에 점수가 비슷한 다른 골짜기가 있다. 조대 단계에서 1등 하나만
정밀화하면 잡음에 따라 엉뚱한 쪽이 1등이 되고 정밀 단계는 거기서 못 빠져나온다.
실측에서 같은 자리를 연속으로 재는데 x 가 1.56 과 1.87 로 갈렸다.

정밀화까지 해 보면 우열이 분명하다 — **1.87 은 오차 0.011, 1.56 은 0.017.** 그래서
서로 떨어진 상위 후보 `coarse_topk`(기본 6)개를 **전부 정밀화한 뒤 마지막에 비교**한다.
초정밀 단계는 비싸므로 이긴 하나에만 돌린다.

> 후보를 고를 때 서로 가까운 것은 하나로 친다(`_push` 의 `nms_xy` 0.12 m). 억제하지
> 않으면 최적점 하나 주변의 격자점들이 목록을 다 차지해서, 정작 멀리 떨어진 다른
> 골짜기가 후보에 못 든다.

### 남은 잔차는 도면과 실물의 차이다

정렬이 완벽해도 스캔점이 도면 벽에 딱 붙지는 않는다. 축척을 자유롭게 풀어 봐도
0.98~1.02 가 전부 비슷하므로(아래) **크기 문제가 아니라 실제 미로가 도면과 1 cm쯤
다르게 지어진 것**이다. 소프트웨어로 더 줄일 수 없다.

| 축척 | 0.96 | 0.98 | 1.00 | 1.02 | 1.04 |
|---|---|---|---|---|---|
| 평균 잔차 | 20.3 mm | 17.2 mm | 17.4 mm | 17.5 mm | 19.1 mm |

RViz 에서 노란 스캔선과 파란 띠가 겹치지 않아 보이는 것도 상당 부분은 착시다.
파랑은 `/map_diff_markers` 의 **"도면에는 벽이 있는데 SLAM 이 아직 못 본 칸"** 이고,
라이다는 벽의 **앞면만** 본다. 도면 벽 두께가 0.05 m 이니 뒤쪽 3~4칸은 정렬이
완벽해도 계속 파랗게 남는다.

### ★ 한 번 재고 믿으면 안 된다 — 측정 합의 (align_repeats)

위 게이트를 고치고 나니 이번엔 **불안정한 값을 실제로 주입**하게 됐다. 아무것도 안 하던
것보다 나쁠 수 있다. 정지한 로봇을 연속으로 재 봤더니:

```
1회  x 1.64  y 1.45  yaw 341.0   오차 0.0388
2회  x 1.73  y 1.10  yaw   0.0   오차 0.0346
3회  x 1.70  y 1.28  yaw   5.5   오차 0.0400
4회  x 1.88  y 1.36  yaw   1.5   오차 0.0353
```

**y 가 35 cm, yaw 가 32도 벌어졌는데 오차는 전부 0.035~0.040 으로 사실상 동률**이다.
점수 표면이 평평하다는 뜻이다. 이 미로는 같은 빗살이 규칙적으로 반복돼서 스캔을 옆 칸으로
통째로 밀어도 거의 똑같이 맞는다. 탐색 범위를 좁혀도(`xy_range:=0.12 yaw_range:=20`)
1.76/1.45/352.5 와 1.56/1.35/341.0 으로 20 cm 벌어졌다.

> 주의 — 이 측정들은 세션이 내려가기 직전에 잰 것이라, 흔들림의 원인이 도면의
> 자기유사성인지 그 사이 로봇이 건드려진 탓인지까지는 못 갈랐다. 어느 쪽이든
> 아래 안전장치는 옳게 동작한다.

그래서 **`align_repeats`(기본 3)번 독립적으로 재서 서로 일치할 때만 적용**한다.
일치 기준은 `agree_xy`(0.05 m) / `agree_yaw`(5.0도). 일치하면 중앙값(각도는 원형평균)을
쓰고, 안 맞으면 **아무것도 적용하지 않고 사용자가 지정한 start 값을 지킨다** —
그리고 왜 포기했는지 에러로 남긴다.

위 실측값을 그대로 넣어 판정을 확인했다:

| 경우 | 위치 벌어짐 | 각도 벌어짐 | 판정 |
|---|---|---|---|
| 실측 전역탐색 4회 | 350 mm | 32.1도 | 거부 (지정값 유지) |
| 실측 범위 좁힌 2회 | 200 mm | 11.5도 | 거부 (지정값 유지) |
| 일치하는 경우 | 10 mm | 1.0도 | 적용 |
| 359도/0도/1도 (0-360 걸침) | 0 mm | 2.0도 | 적용 (원형평균 360.0) |

정렬이 계속 거부되면 도면만으로는 자리를 특정할 수 없다는 뜻이다. 그때는 로봇을 정해진
자리에 두고 `auto_align:=false` 로 지정값을 쓰거나, `xy_range` / `yaw_range` 를 좁혀서
그 근처만 보게 하면 된다.

### 기준 도면 수정판 — maps/final_map.yaml (기본값)

원본 `map_compare/custom_maps/maze_195x162` 는 오른쪽 세로 바가 위/아래 구석
바깥벽과 어긋나 있었다. 벽 두께는 전부 0.050 m 인데:

**원본 파일은 그대로 둔다.** 되돌리려면:

### allow_reverse — 뒤쪽 목적지는 180도 돌지 말고 후진 (기본 false)

목적지가 로봇 뒤에 있으면 제자리에서 180도 도는 것은 순전한 낭비다. 그냥 뒤로 가면 된다.
매 주기 "앞으로 갈 때의 방향오차"와 "뒤로 갈 때의 방향오차"를 비교해 **덜 도는 쪽**을
고른다. 후진은 `s`(= `M -255 -255`)로, 역시 keyboard_test 로 검증된 명령이다.

정확히 뒤쪽 0.9 m 목적지로 시뮬레이션한 결과:

| | 총 회전량 | 사용한 명령 |
|---|---|---|
| `allow_reverse:=true` | **0°** | 후진 32회 |
| `allow_reverse:=false` | **190°** | 전진 33회 |

* 앞뒤 판단이 경계에서 덜덜거리지 않도록 `reverse_hysteresis`(기본 0.30 rad) 만큼
  확실히 유리할 때만 전환한다. ㄱ자 경로 시험에서 전환 0회.
* **후진 중에는 라이다 뒤쪽 부채꼴**(±20°)을 본다. 앞만 보면 후진할 때 무방비다.
* 항상 앞을 보고 주행하게 하려면 `allow_reverse:=false`.

### 경로를 안 따라가고 엉뚱한 방향으로 갈 때 — invert_angular

로봇이 **움직이기는 하는데** 초록 경로를 안 따라가고 계속 벗어난다면, 회전 방향
부호가 반대일 가능성이 높다. 모터 좌/우가 뒤바뀌어 배선돼 있으면 `angular>0`
(ROS 규약상 좌회전)에 로봇이 오른쪽으로 돈다. 그러면 조향이 오차를 줄이는 게
아니라 **키우는 양의 되먹임**이 되어 절대 수렴하지 않는다.

추종기가 이걸 자동으로 진단한다. 보낸 회전명령과 TF 로 관측한 실제 yaw 변화의
상관을 40샘플 누적해서 판정하고, 이런 메시지를 띄운다.

```
[ERROR] 회전 방향이 반대입니다! 좌회전 명령에 로봇이 오른쪽으로 돕니다 (누적 -4.00 rad).
        이 상태로는 조향이 오차를 키우기만 해서 경로를 절대 못 따라갑니다.
        → invert_angular:=true 로 다시 실행하세요.
```

```bash
ros2 launch ~/auto_drive/auto_drive.launch.py invert_angular:=true
```

정상이면 `회전 방향 정상 확인 (누적 +4.00 rad)` 가 뜬다.
전진 명령에 뒤로 가면 `invert_linear:=true` 도 있다.

네 가지 조합을 시뮬레이터로 검증한 결과:

| 배선 | invert_angular | 결과 | 진단 메시지 |
|---|---|---|---|
| 정상 | false | 도착 | 정상 확인 |
| 반대 | false | **미도착** | 반대입니다 → true 로 |
| 반대 | true | 도착 | 정상 확인 |
| 정상 | true | **미도착** | 반대입니다 → false 로 |

### control_mode — 제어 방식 (기본 `keys`)

`keys` 모드는 **keyboard_test.py 로 잘 움직였던 명령 네 가지만** 사용한다.
전진과 회전을 절대 섞지 않으므로, UART 로 나가는 바이트가 키보드 조작과 동일하다.

| 명령 | keyboard_test | 아두이노가 받는 값 |
|---|---|---|
| 전진 | `w` | `M 255 255` |
| 좌회전 | `a` | `M -255 255` |
| 우회전 | `d` | `M 255 -255` |
| 정지 | 키 뗌 | `M 0 0` |

비례제어가 없으므로 두 가지로 보완한다.

* **히스테리시스** — 방향 오차가 20° 를 넘으면 회전 시작, 9° 아래로 들어오면 종료.
  하나의 문턱값만 쓰면 경계에서 좌우로 덜덜거린다.
* **펄스** — 회전은 4주기 ON / 2주기 OFF (20Hz 기준 0.2초 켜고 0.1초 끔).
  PWM 255 밖에 없어서 계속 돌리면 오버슛한다. 목적지 0.45 m 안에서는 전진도
  2 ON / 2 OFF 로 펄스를 걸어 감속한다.

조정: 회전이 과하면 `turn_pulse_on:=2`, 너무 굼뜨면 `turn_pulse_off:=1`.
비례제어를 쓰려면 `control_mode:=smooth`.

### turn_mode — 큰 방향전환 방식 (`control_mode:=smooth` 일 때만)

이 차체는 **제자리 회전을 못 한다.** `M 255 -255`(좌우 역방향, PWM 최대)를 보내도
꿈쩍하지 않는 것을 실측으로 확인했다. 4륜 메카넘이 제자리에서 돌려면 네 바퀴가
바닥을 비벼야 해서 토크·전류가 최대로 필요하기 때문이다.
반면 `M 255 255`(전진)는 잘 움직인다.

| | 동작 | 바퀴 명령 |
|---|---|---|
| `arc` (기본) | 전진하면서 최대 조향 | 안쪽 0 / 바깥쪽 255 — **역회전 없음** |
| `spin` | 제자리 회전 | 안쪽 −255 / 바깥쪽 +255 |

`arc` 는 `|angular| <= |linear|` 를 **발행 직전 값**에 강제해서 안쪽 바퀴가 절대
역회전하지 않게 한다. 한쪽 정지 + 반대쪽 전속이므로 회전반경은 바퀴간격의 절반
(≈ 0.06 m)으로 충분히 작다.

> `|ang| <= lin` 제약은 목표값이 아니라 **가감속을 거친 최종 값**에 걸어야 한다.
> 회전 램프(0.15/주기)가 전진 램프(0.04/주기)보다 빨라서, 목표값에만 걸면
> 가속 중에 안쪽 바퀴가 순간적으로 역회전한다. (실제로 PWM −147 까지 내려갔었다)

제자리 회전이 되는 차체로 바꿨다면 `turn_mode:=spin` 을 주면 된다.

`arc` 모드에서는 전진 없이 방향을 바꿀 수 없으므로, 앞이 막히면 완전 정지한다.
그때는 로봇을 앞이 트인 곳으로 옮기거나 `use_scan_guard:=false` 로 두면 된다.
* **도착**: 목적지까지 거리 ≤ `goal_tolerance`(0.12 m) → 모터 정지 + 메시지 출력.

## 4. 충돌 회피 (차체 크기 반영)

1차 방어는 **경로 자체**다. `path_planner_node.py` 가 차체 폭 0.123 m 의 절반 + 여유 0.02 m
만큼 벽을 부풀린 뒤 A* 로 경로를 뽑기 때문에, 그 경로를 정확히 따라가면 벽에 안 닿는다.
RViz 의 `4_부풀린벽(차체여유)` 레이어가 그 금지영역이다.

2차 방어로 추종기가 `/scan` 의 **앞쪽 ±20° 부채꼴**을 본다.

* 거리 ≤ `차체길이/2 + 0.06 m` (기본 0.155 m) → **전진만 정지**, 회전은 허용
  (제자리 회전으로 경로 방향에 맞춰 빠져나갈 수 있게. 완전 정지시키면 벽 앞에서 갇힌다)
* 그보다 조금 멀면 → 거리에 비례해 감속

부채꼴을 좁게(±20°) 잡은 이유: 경로가 벽에 0.08 m 까지 붙을 수 있어서, 넓게 잡으면
정상 주행 중에도 옆벽 때문에 계속 멈춘다.

끄려면 `use_scan_guard:=false`, 거리를 바꾸려면 `obstacle_stop_distance:=0.20`.

| 토픽 | 타입 | 설명 |

도착 확인 / 수동 정지:

```bash
ros2 topic echo /auto_drive/goal_reached
ros2 topic echo /auto_drive/status

ros2 topic pub --once /auto_drive/cancel std_msgs/Empty "{}"             # 취소
```

## 8. 문제 해결

| 증상 | 확인할 것 |
|---|---|
| `현재 위치(TF map->base_link)를 못 받았습니다` + cartographer 가 `Queue waiting for data: (0, scan)` | **라이다 미연결**이 대부분이다. 아래 "라이다가 안 붙었을 때" 참고 |
| 경로는 그려지는데 안 움직임 | `ros2 topic echo /cmd_vel` 로 명령이 나가는지 → 나가면 UART 노드/포트 문제, 안 나가면 `/auto_drive/status` 확인 |
| 명령은 나가는데 바퀴가 안 돎 | UART 노드/포트, 전원 전압, 바퀴 걸림을 확인한다. 비정지 명령은 이미 PWM 255다 |
| 벽 앞에서 계속 `장애물 정지` | `obstacle_stop_distance` 를 줄이거나 `front_sector_deg` 를 좁힐 것. 급하면 `use_scan_guard:=false` |
| 코너에서 바깥으로 벌어짐 | `lookahead` 를 0.20 정도로 줄일 것 |
| 목적지 근처에서 왔다갔다 | `goal_tolerance` 를 키울 것 (0.15) |
| `경로 없음 — 통로가 차체보다 좁거나 막혀 있습니다` | 경로계획 쪽 문제. `safety_margin:=0.01` 로 줄여볼 것 |

### 라이다가 안 붙었을 때 (경로는 그려지는데 로봇이 안 움직임)

`path_planner_node.py` 는 **기준 도면 파일만** 보고 경로를 그리기 때문에 (출발점은 map 원점 0,0 으로 가정)
라이다·SLAM 이 없어도 초록 경로는 정상적으로 나온다. 하지만 추종기는 실제 현재 위치가 있어야
움직이므로, SLAM 이 없으면 안전하게 정지 상태를 유지한다.

```bash
ls /dev/ttyUSB*                 # 라이다 포트가 잡혔는지 (없으면 미연결)
lsusb | grep -iE "cp210|ch34|ftdi|silicon"   # USB-시리얼 칩이 보이는지
ros2 topic hz /scan             # 스캔이 실제로 들어오는지
ros2 run tf2_ros tf2_echo map base_link      # 위치가 나오는지
```

* `/dev/ttyUSB*` 가 아예 없다 → 라이다 USB 케이블을 꽂을 것
* 다른 번호로 잡혔다 → `lidar_port:=/dev/ttyUSB1` 로 실행
* 있는데 권한 오류 → `sudo usermod -aG dialout $USER` 후 재로그인

정상이면 launch 로그에 `Queue waiting for data: (0, scan)` 경고가 사라지고
`tf2_echo map base_link` 가 좌표를 출력한다. 그 뒤에 목적지를 찍으면 출발한다.
